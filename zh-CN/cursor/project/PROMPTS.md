## 1. 需求分析（`/rd-requirement`）

```text
使用 /rd-requirement

## 背景
{项目/产品/系统背景，1-3 句话}

## 用户原始需求
{保留用户原始表述，不要改写}

## 已知约束
- 目标用户 / 干系人：{角色}
- 业务流程或政策约束：{如有}
- 技术或系统约束：{如已知，否则写“待定”}
- 合规 / 标准约束：{如有}
- 时间 / 预算 / 资源约束：{如有}

## 期望产出
产出 PRD / SRS，包含优先级、假设、排除项、追踪关系和可验证验收标准。
```

```text

请分析以下已有需求材料，补齐缺失维度：

## 已有材料
{粘贴文本或引用文件路径}

## 重点关注
- {如：干系人角色不清}
- {如：非功能需求缺失}
- {如：验收标准不可验证}
- {如：排除范围不明确}
```

## 3. 研究证据（`/rd-research`）

当外部证据会实质影响可研、技术方案、标准规范、详细设计决策或事实依赖型评审时使用本模板。若用户提供的材料已经足够支撑小任务，可跳过。

```text
使用 /rd-research

## 研究目标
{需要证据支撑的决策、文档章节、标准条款、技术选型、政策问题或评审结论}

## 下游用途
这些证据将支撑：{rd-feasibility / rd-solution / rd-specification / rd-design / rd-writing / rd-review}

## 所需来源类型
- 目标项目文档：{文件或摘录}
- 标准 / 政策 / 法规：{如相关}
- 厂商 / 框架 / 协议文档：{如相关}
- 学术或技术文献：{如相关}
- 市场、成本或行业案例：{如相关}

## 期望产出
产出来源表，包含权威性、日期/版本背景、相关性、置信度、冲突、缺口和可引用笔记。暂不编写最终下游文档。
```

选择一种主研究模式：{证据支撑 / 技术与开源研究 / 配置与基础设施研究 / 事实核查与论证证据}。技术和配置任务还应包含准确产品形态、版本、平台、环境、可复现状态、安全/隐私边界，以及回退或退出路径证据。

## 15. 绿地开源格局研究与方案门禁

仅当绿地产品、工具或尚未解决的架构决策会因比较外部项目而获得实质收益时使用。不得用于小修复或已批准架构下的实现。

只需要单一方案交付物时，使用 `/rd-solution`，并把外部证据交给 `/rd-research`。只有用户明确要求把研究、暂定 MVP 需求、方案选择和批准门禁编排为多制品任务时，才使用 `/rd-delivery`。

```text
使用 /rd-delivery

## 目标与授权边界
我要开发 {产品或工具}。当前控制目标是形成有证据支撑的方案决策，不是进入实现。

## 研究边界
- 当前阶段只进行只读研究和方案定义。
- 未另行授权时，不修改目标项目的源码、配置或实现制品，不输出实现代码，不进入实现。
- 持久化交接记录：{已批准路径 / 未授权；默认未授权}。使用 `/rd-delivery` 且路径已获明确批准时，只写入保存制品状态、决策、证据缺口和批准门禁所必需的有边界交付记录；否则在聊天中返回决策包，并说明未创建持久化交接。
- 是否允许在 `.tmp/local/` 建立临时只读克隆：{允许 / 不允许}。不允许时，应说明由此产生的源码检查限制。

## 需要与约束
{用户、问题、核心场景、固定业务约束、安全/隐私要求、目标平台、预算/进度限制、集成约束、排除项和成功标准}

## 来源纪律
GitHub 是候选来源，不是唯一权威。
- 记录检查日期，并把每个重要仓库固定到 tag 或 commit。
- 按需检查官方文档、源码、Release、Issue/PR 维护情况、安全公告、许可证、依赖和可复现证据。
- 使用 Release/commit 时效、维护者响应、归档状态和未解决关键问题评估活跃度；不得主要按 star 排名。
- 区分维护者声明、静态源码检查和已经复现的运行行为。

## 候选分析
对每个高价值候选说明其解决的问题、架构、主要依赖、扩展与信任边界、当前维护状态、值得复用和应避免的设计、适用性缺口、许可证/安全约束，以及退出或替代路径。

## 必要决策包
1. 可追踪证据表和候选短名单，包括被淘汰候选及理由。
2. 推荐技术选型和最强可信替代方案。
3. 系统上下文、组件架构、数据/控制流、信任边界和关键失败路径。
4. 与用户需要关联的暂定 MVP 范围、排除项、假设和可验证验收条件。
5. 考虑依赖关系的实现交接顺序、主要风险、验证门禁和未决决策。

## 批准门禁
提交决策包后，在批准门禁处停止。实现不属于 RD Skills 的交付边界；没有单独确认和具备实现能力的工作流，不得开始实现。
```

## 16. 高影响决策的双向论证与关键澄清

这是可选前置段，不是独立 Skill。仅当高影响问题存在真实立场或方案分歧，且尚未解决的关键变量可能实质改变结论时，才把它附加在适用的 `/rd-requirement`、`/rd-feasibility`、`/rd-solution` 或 `/rd-review` 提示词前。不得用于明确事实查询、小范围修正、已批准方案下的实现或其他低风险工作。

```text
在形成最终判断前：

1. 保留我的原始问题，并以“当前理解”重述目标。区分底层需要、我提出的方案、已确认约束和未经确认的假设，不要替我虚构目标。
2. 识别隐含假设和影响决策的证据缺口，并说明不同取值或核实结果可能如何改变结论。先从所给材料、当前项目或权威来源中核实能够自行发现的事实，不要让我重复提供你可以自行检查的信息。
3. 给出支持我当前想法的最强可信论证，以及最强可信且实质性的反驳、替代解释或替代方案。不要为了形式制造对称；如果一方的证据明显更弱，应明确说明。
4. 指出真正的分歧源于事实、定义、目标、价值、风险偏好还是决策权归属，并识别最可能改变结论的关键变量。如果可从当前问题和证据判断，再指出最可能导致错误判断的一个错误或失败模式；否则省略。
5. 如果存在一个或多个仍未解决、只能由我作出且会阻塞最终判断的决策问题，先询问影响最大的阻塞问题；问题相互独立时可小批量询问。继续推进不依赖答案的已授权工作，并在阻塞决策解决前暂缓受影响的判断。没有此类阻塞决策时，不要为了形式提问；直接给出有边界的判断、理由、置信度、剩余不确定性和下一步行动。

不要输出隐藏思维链。只输出可审查的当前理解、假设、证据、反证、关键变量、权衡和结论摘要。
```

## 17. 可选的授权范围与完成条件

仅当文档交付任务的授权范围或停止位置需要明确时，将这个可选块加入提示词。只填写影响当前任务的字段；范围已经清楚的常规任务可以省略。它在适用规则下记录本次任务的具体选择，不新增审批流程，也不授予扩大范围的权限。

```text
已授权工作：{只读分析 / 指定制品的起草或修改 / 必要的文档验证}
可自行处理：{不改变关键结论、范围或效力的低风险细节}
需要我决定：{会影响范围、关键约束、制品状态或外部影响的未决事项}
完成条件：{交付物、适用检查，以及明确保留的未验证项}
停止边界：{不属于本次任务的后续动作或阶段}
```

已核验的草稿或建议可以构成本次工作的完整交付，同时保留待干系人批准状态。批准、建立基线、发布和下游执行分别需要相应授权与证据；不能从这个填写块中推定获得。

## 组合使用示例

```text
# 对用户明确要求的多文档或跨会话任务，使用 /rd-delivery 只编排下列必要步骤。

# 第 1 步：需求分析
使用 /rd-requirement
将用户原始诉求结构化为 PRD，包含优先级、假设、排除项和验收标准。

# 第 2 步：需求评审
使用 /rd-review，需求评审模式
评审 PRD 的完整性、可验证性、一致性和边界清晰度。

# 可选：研究证据
使用 /rd-research
当可研、方案、标准、设计或评审结论依赖文献、标准、政策、厂商文档、成本假设、成熟度结论或行业案例时，先收集并核验证据。

# 可选：专业写作
使用 /rd-writing
当实际交付物是面向受众的技术文章、证据报告或决策简报时，把已核实证据组织成稿。

# 第 3 步：可行性分析
使用 /rd-feasibility
从技术、经济、进度、运行、合规和风险维度判断项目是否可行。

# 第 4 步：技术方案 / 概要设计
使用 /rd-solution
基于 PRD 和可研结论编写技术方案，比较候选方案并给出推荐。

# 第 5 步：方案评审
使用 /rd-review，方案评审模式
评审需求覆盖、架构依据、风险、成本和设计层面的部署架构。

# 第 6 步：详细设计
使用 /rd-design
产出指定模块的详细设计，包含接口、数据、流程、错误、安全和并发。

# 第 7 步：设计评审
使用 /rd-review，设计评审模式
评审详细设计的完整性、可追溯性、正确性和未决决策。

# 可选：标准规范工作
使用 /rd-specification
以条款级证据和规范性用语起草或修订标准/规范条款。
```

## 提示词使用技巧

| 技巧 | 说明 |
|------|------|
| 保留原始文本 | 结构化前先保留用户原始需求、条款或文档原文 |
| 明确文档类型 | PRD、可研报告、技术方案、概要设计、详细设计、标准、技术文章、证据报告、决策简报或评审报告 |
| 引用上游输入 | 用 PRD -> 可研 -> 方案 -> 详细设计 -> 评审维持追踪关系 |
| 有选择地使用研究 | 只有外部证据会实质影响下游文档或评审时才调用 `/rd-research` |
| 要求证据分层 | 要求区分事实、假设、估算、推断和未知项 |
| 指定评审重点 | 聚焦评审比泛泛地说“帮我评审”更有效 |
| 标准任务强调规范性 | 标准评审要有条款定位、替换文本和“需人工核实”标注 |
| 排除执行任务 | 不要求这些 Skill 写代码、跑测试、部署或操作系统 |
